Architecture

Channel Topology

The system is a pipeline of async tasks connected by tokio::sync::mpsc channels. A single broadcast::channel fans events out to all downstream consumers.

Channel chain (left to right):

  1. Gateways (FixAcceptor, WsServer) — receive orders from external clients, parse them into OrderCommand, and send on gateway_cmd_tx: mpsc::Sender<OrderCommand>.
  2. Latency middleware — optional async task that reads from latency_cmd_rx, applies per-participant delay via LatencySimulator (Box-Muller normal sampling), then forwards to pretrade_cmd_tx.
  3. PretradeActor — standalone task that reads from pretrade_cmd_rx, runs the full 11-point risk pipeline on New orders, forwards passing commands to engine_cmd_tx, and emits OrderRejected events directly to the broadcast channel for failing orders.
  4. MatchingEngine — HashMap<String, MatchingEngine> (one per instrument) in the main event loop. Receives commands on engine_cmd_rx, dispatches to the correct engine, collects events.

Event return path:

  • Events from the engine (Vec<ExchangeEvent>) are assigned a global sequence number, wrapped in Arc<SequencedEvent>, and broadcast on event_tx: broadcast::Sender<Arc<SequencedEvent>>.
  • Consumers subscribe via event_tx.subscribe(): FixAcceptor (per-session MD & ER), WsServer (per-subscriber MD), TUI, EventWriter, PretradeActor (to track state), Postrade (inline in main loop).

Event Fan-Out

A single broadcast::channel<Arc<SequencedEvent>>(4096) is created in main(). The main event loop is the exclusive producer.

Main loop flow

#![allow(unused)]
fn main() {
loop {
    tokio::select! {
        Some(cmd) = engine_cmd_rx.recv() => {
            // 1. Dispatch to the correct engine by cmd.instrument()
            let events = engine.process(cmd);

            // 2. Process events inline (postrade, metrics, logging)
            process_events_and_fan_out(events, &event_tx, ...).await;

            // 3. Every event gets a global sequence number
            global_seq += 1;

            // 4. Wrap and broadcast
            let arc = Arc::new(SequencedEvent { sequence: global_seq, event });
            let _ = event_tx.send(arc);

            // 5. Persist to PostgreSQL
            event_writer.write(arc).await;
        }
        _ = ctrl_c => break;
    }
}
}
  • ClockTick commands are broadcast to all engines (session transitions, expiry scans).
  • All other commands are routed to the specific engine by cmd.instrument().

Lag handling

If a consumer is too slow, broadcast::Receiver::recv() returns RecvError::Lagged(n). The consumer must drop and re-subscribe, requesting a re-snapshot of its subscribed instruments to catch up. Lag metrics are tracked via record_persist_lag_seq().

Snapshot & Recovery Flow

Creating snapshots

The main loop checks after each command whether any instrument has accumulated enough events to trigger an automatic snapshot:

events_since_snapshot[instrument] >= snapshot_every_events

When triggered:

  1. Call MatchingEngine::serialize_snapshot(global_seq) which produces an EngineSnapshot containing:
    • sequence — the global sequence at the time of snapshot
    • session_state — JSON serialized SessionState
    • clob_state — BTreeMap<Price, Vec<RestingOrder>> serialized to JSON
    • stop_book_state / expiries_state — reserved for future use
    • state — ref_price, last_trade_price, instrument name
  2. Write to the snapshots table via EventWriter::write_snapshot().
  3. Reset the per-instrument counter (reset_snapshot_count).

Recovery on restart

When main() starts with a PostgreSQL connection:

  1. Load persist_meta — get last_sequence (the global sequence of the last persisted event). If zero, there is nothing to recover.
  2. Load snapshots — for each instrument, SELECT DISTINCT ON (instrument_id) ... FROM snapshots ORDER BY instrument_id, snapshot_at DESC — get the most recent snapshot.
  3. Load events — SELECT sequence, payload FROM events WHERE sequence > snapshot.sequence ORDER BY sequence ASC. If no snapshot exists for an instrument, load events from sequence 0.
  4. Replay — for each instrument with a snapshot, call MatchingEngine::apply_snapshot(snapshot) (restores session state via force_state(), CLOB state via deserialize_state(), reference price).
  5. The engine is now ready for new orders at the correct state.

SimClock Threading

The SimClock trait provides business logic time. It is dispatched from a separate async task.

Clock modes

ModeImplementationBehavior
realtimeRealTimeClocknow() returns chrono::Utc::now() directly. 1 wall second = 1 sim second.
acceleratedAcceleratedClocknow() returns sim time advanced by elapsed_wall * clock_speed. Supports set_factor(), pause(), resume().
replayReplayDrivenClockset_time() is called by the replay loop as it reads an NDJSON feed. Clock time is driven by the data, not wall time.

ClockDriver

ClockDriver::new(sim_clock: Arc<dyn SimClock>)

ClockDriver::run(cmd_tx) is a standalone async task that:

  1. Reads clock.wall_per_sim_sec() to determine the tick interval.
  2. Sleeps for that interval (using tokio::time::sleep — allowed here because ClockDriver is infrastructure, not business code).
  3. Calls clock.now() to get the current sim time.
  4. Sends OrderCommand::ClockTick { sim_time } on gateway_cmd_tx.

Replay mode

In replay mode, ClockDriver is not used. Instead, a replay task reads an NDJSON feed line-by-line, calls replay_clock.set_time(record_time), and injects OrderCommand::ClockTick into the command channel with a small delay between records. When the feed is exhausted, the task exits.

Gateway annotation

Gateways read sim_clock.now() (via Arc<dyn SimClock>) to annotate outgoing messages with sim_time. This is done on each message build, not from the clock tick.

Config Hot-Reload

The notify crate watches two directories for file system changes:

  • instruments/ — TOML files defining InstrumentConfig entries
  • participants/ — TOML files defining ParticipantConfig entries

Reload flow

  1. notify::Watcher detects a file change (create, modify, remove) in a watched directory.
  2. The respective registry (InstrumentRegistryImpl or ParticipantRegistryImpl) re-reads all TOML files in the directory.
  3. On successful reload, the registry broadcasts a ChangeNotification to all subscribers (engines, FIX sessions).
  4. Engines apply new instrument configs on the next ClockTick — they do not apply mid-cycle.

Registry internals

  • InstrumentRegistryImpl: Arc<RwLock<BTreeMap<String, Arc<InstrumentConfig>>>>
  • ParticipantRegistryImpl: same pattern for participants
  • Both expose get(id: &str) -> Option<Arc<Config>> and all() -> Vec<Arc<Config>>
  • Both expose subscribe_changes() -> broadcast::Receiver for hot-reload notifications

Partition Strategy

The events table uses PostgreSQL’s native partitioning with PARTITION BY RANGE (occurred_at).

Partition management

ensure_current_partition() in nadatrade-persist/src/partition.rs is called once at startup and on every EventWriter::flush() call:

  1. Compute the current month boundary (YYYY-MM-01).
  2. Compute the next month boundary (handling year rollover).
  3. Cached via last_partition_month field on EventWriter — one DB round-trip per month, not per flush.
  4. Issue CREATE TABLE IF NOT EXISTS events_yYYYYMM PARTITION OF events FOR VALUES FROM ('YYYY-MM-01') TO ('YYYY-MM-01').

This ensures that the partition for the current month always exists without requiring manual partition creation scripts.

Partition names follow the pattern events_y2026m06 (with a month-leading-zero format). The current implementation uses format!("events_y{:04}{:02}", year, month) producing names like events_y202606.

PretradeActor

The PretradeActor sits as a standalone task in the channel chain between the latency simulator and the matching engine.

Channel position

mpsc::Receiver<OrderCommand> ← pretrade_cmd_rx
mpsc::Sender<OrderCommand>   → engine_cmd_tx    (forward passing orders)
broadcast::Sender             → event_tx          (emit rejects)

Full 11-point pipeline

For OrderCommand::New commands, the actor runs check_order() which performs all 11 checks:

  1. Quantity > 0 — reject zero or negative qty.
  2. Price field validation — Market orders require no price; Limit/StopLimit require price.
  3. Stop field validation — Stop/StopLimit require stop_price; Limit/Market must not have one.
  4. Unknown instrument — instrument ID not in InstrumentRegistry.
  5. Unknown participant — participant ID not in ParticipantRegistry.
  6. Participant not active — participant is disabled.
  7. Instrument limits — min_qty, max_qty, lot_size, tick_size compliance.
  8. Price band — price within [ref_price * (1 - band), ref_price * (1 + band)].
  9. Fat finger protection — order price within fat_finger_pct of last trade price.
  10. Notional limit — qty * price <= max_notional_per_order.
  11. Duplicate ClOrdID — checks active_order_ids set (tracked via event stream subscription).

Non-order pass-through

The following commands are forwarded unconditionally without risk checks:

  • ClockTick — session advancement
  • SessionTransition — manual state changes
  • Scenario — scenario injection
  • Cancel / Replace / Snapshot — non-order mutations

State tracking

The PretradeActor subscribes to the event broadcast to maintain two internal maps:

  • active_order_ids: HashSet<(participant, instrument, client_order_id)> — insert on OrderAccepted/OrderReplaced, remove on OrderCancelled. Used for duplicate ClOrdID detection.
  • last_trade_prices: HashMap<instrument, Decimal> — updated on TradePrinted. Used for fat finger check (order price vs last trade price).
  • ledgers: HashMap<participant, Ledger> — updated inline on TradePrinted via apply_fill(). Used for position-limit risk check.

These maps use Arc<StdMutex<...>> so the background event subscriber and the command processing loop can share state safely.

Reject path

When a check fails, the actor does not send the command to the engine. Instead, it constructs an ExchangeEvent::OrderRejected with the appropriate RejectReason and injects it directly into the broadcast channel. The gateway that originated the order receives the reject via its event subscription and sends the client a FIX OrderCancelReject (35=9) or WS rejected message.
