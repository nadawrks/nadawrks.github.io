NadaTrade Documentation

FIX 4.2 Gateway

The FIX 4.2 gateway provides an industry-standard Financial Information eXchange protocol interface for order entry, cancel/replace, market data, and session-level control. It listens for TCP connections, authenticates participants via username/password on logon, and translates between FIX wire messages and the internal NadaTrade command/event model.

Architecture

The gateway consists of four components:

  • FixAcceptor (crates/nadatrade-fix/src/acceptor.rs) — binds a TCP listener on the configured listen_address (default 0.0.0.0:9823). On each inbound connection, it spawns a handle_connection task that owns the TCP stream for the lifetime of that session.
  • FixSession (crates/nadatrade-fix/src/session.rs) — per-connection state machine. Parses inbound FIX messages, validates session-level rules (logon, sequence gaps, role enforcement), and produces OrderCommand values for the matching engine or MdSubscription records for market data.
  • codec (crates/nadatrade-fix/src/codec.rs) — pure-function builders and parsers for FIX message wire format (tag=value pairs separated by SOH, BodyLength, CheckSum).
  • MessageStore (crates/nadatrade-fix/src/store.rs) — file-backed append-only journal used for ResendRequest replay.

Data flows through the gateway in two directions:

TCP client ──► FixSession.handle_message() ──► OrderCommand ──► cmd_tx ──► MatchingEngine
                                                                     │
broadcast event_rx ◄── ExchangeEvent ◄── MatchingEngine             │
        │                                                             │
        ▼                                                             │
  event_to_fix_bytes() / MD snapshot builders                         │
        │                                                             │
        ▼                                                             │
  TCP writer (ExecutionReport / MD snapshot) ──► TCP client

The gateway subscribes to the global event bus (broadcast::Receiver<Arc<SequencedEvent>>) and filters events relevant to each session (by client_order_id or participant identity) to produce unsolicited ExecutionReport (35=8) messages. Market data subscriptions cause BookUpdated events to be translated into MarketDataSnapshot (35=W) and TradePrinted events into MarketDataIncrementalRefresh (35=X).

Connection Lifecycle

TCP Framing

Every FIX message is a sequence of tag=value pairs separated by the SOH character (\x01). The message is framed by:

  1. BeginString — tag 8, always FIX.4.2.
  2. BodyLength — tag 9, the number of bytes between the delimiter after 9=<n> and the delimiter preceding 10=. The codec uses a sentinel placeholder (__BODY_LEN__) during construction and substitutes the computed length before checksum calculation.
  3. CheckSum — tag 10, computed as the sum of all preceding bytes (including SOH delimiters) modulo 256, formatted as a 3-digit zero-padded number. The message terminates with a trailing SOH after the checksum.

The acceptor’s extract_complete_messages function scans the accumulated TCP buffer for 8=FIX.4.2\x01, parses the BodyLength to determine the message extent, then slices complete messages from the stream. Incomplete frames are retained in the buffer for the next read() cycle.

Heartbeat Timer

A dedicated task spawned per connection sends server-initiated Heartbeat (35=0) messages every heartbeat_secs seconds (configurable, default 30). Each heartbeat carries the current outgoing sequence number (34) and the sender/target comp IDs (49/56). If the client does not respond, the TCP connection will eventually be detected as broken by the OS.

Logon (35=A)

Before any order or market data message is accepted, the client must send a Logon message. The gateway enforces this: any message with type other than A received before logon is rejected with a SessionReject (35=3) containing 58=Session not logged on; send Logon first.

The server’s Logon response echoes the agreed parameters:

8=FIX.4.2\x019=<len>\x0135=A\x0134=<seq>\x0149=NADATRADE\x0156=<SenderCompID>\x01108=30\x0198=0\x0110=<cksum>\x01

Authentication Flow

  1. The client sends 35=A with 553 (Username) and 554 (Password).
  2. If credentials is not configured (an empty HashMap), the logon is accepted unconditionally — SenderCompID and TargetCompID are set from the message, and the session transitions to connected = true.
  3. If credentials are configured, the gateway looks up the username in the map:
    • Unknown username → Logon rejected. Server sends a Reject (35=3) with 58=Unknown participant. Session remains disconnected.
    • Password mismatch → Logon rejected. Server sends a Reject (35=3) with 58=Invalid credentials. Session remains disconnected.
    • Match → Logon accepted as above.
  4. On successful logon, the server’s component_id and sender_comp_id are set to the client’s SenderCompID from the logon message.

Logout (35=5)

A Logout message (35=5) sets connected = false on the session. No response is sent; the server stops accepting orders. The TCP write task will eventually terminate because the event stream forwarding loop breaks when connection errors occur.

8=FIX.4.2\x019=<len>\x0135=5\x0134=<seq>\x0149=<SenderCompID>\x0156=<TargetCompID>\x0110=<cksum>\x01

Heartbeat (35=0) and TestRequest (35=1)

Heartbeat

The gateway sends server-initiated Heartbeat messages at the configured interval. The message format:

8=FIX.4.2\x019=<len>\x0135=0\x0134=<seq>\x0149=NADATRADE\x0156=<SenderCompID>\x0110=<cksum>\x01

Client-initiated Heartbeats (35=0) received while connected are silently acknowledged (no response). If the session is not connected, a client Heartbeat or TestRequest is rejected with a SessionReject (35=3).

TestRequest

When the client sends a TestRequest (35=1), the server responds with a Heartbeat (35=0). The TestReqID in tag 112 is not echoed in the current implementation.

8=FIX.4.2\x019=<len>\x0135=1\x0134=<seq>\x0149=<SenderCompID>\x0156=<TargetCompID>\x01112=<test-req-id>\x0110=<cksum>\x01

Replace Semantics

The matching engine interprets replacements as follows:

  • Price-only decrease (same or lower qty) — the order retains its position in the book (time priority).
  • Quantity increase or price change to a worse level — the order is removed and re-enters the book at the tail of the new price level.
  • Neither new_qty nor new_price is required; the engine preserves unchanged fields from the original order.

Solicited vs. Unsolicited

  • Solicited: The matching engine processes an incoming command and emits the corresponding event on the event bus in the same processing cycle. The FIX acceptor receives the event via event_rx and translates it to a FIX message.
  • Unsolicited: A resting order is filled by an incoming aggressive order from a different participant. The resting order’s participant receives an ExecutionReport even though they sent no new message.

The event_concerns_session function filters events by matching client_order_id and participant against the session’s tracked set of known order IDs and its logged-in participant identity.

MarketDataRequest (35=V)

The gateway accepts MarketDataRequest messages to subscribe or unsubscribe from instrument-level market data.

Tags Parsed

TagNameValues
262MDReqIDrequest identifier string
263SubscriptionRequestType0=Snapshot only, 1=Snapshot + Updates, 2=Unsubscribe
55Symbolinstrument ID

When SubscriptionRequestType is 2 (unsubscribe), the subscription is removed from the session’s tracking map. Otherwise, a new MdSubscription record is stored keyed by instrument, and the gateway begins forwarding BookUpdated and TradePrinted events as FIX market data messages.

Note: The current implementation parses a simplified MDR format. Repeating groups (NoMDEntryTypes / NoRelatedSym) are not parsed; only the instrument in tag 55 is read. The subscription always delivers full book snapshots and trade prints for that instrument.

Session Control Messages

ResendRequest (35=2)

When the server detects a sequence number gap (the received MsgSeqNum is greater than last_seq_num_in + 1), it sends a ResendRequest asking the client to retransmit missing messages.

TagNameValue
7BeginSeqNoexpected sequence number (last_seq_num_in)
16EndSeqNo0 (unbounded — request all messages from BeginSeqNo)

The gap is detected in handle_message before any message-type-specific processing: if msg_seq_num > self.last_seq_num_in, a ResendRequest is sent immediately and the message is dropped.

Client-to-server ResendRequest: When the client sends 35=2, the server replays messages from the MessageStore. It reads tags 7 (BeginSeqNo) and 16 (EndSeqNo; 0 means “all from BeginSeqNo”) and returns matching outbound messages as a FixSessionResponse::Resend batch. If no MessageStore is initialized (no store directory configured), an empty list is returned.

Reject (35=3) / SessionReject

The gateway sends 35=3 messages for protocol-level errors:

  • build_reject — simple reject with RefSeqNum (45) and Text (58). Used for logon credential failures.
  • build_session_reject — richer reject with Text (58), RefTagID (371), and RefMsgType (372). Used for unknown message types, role violations, and pre-logon messages.

SequenceReset (35=4)

Built by build_sequence_reset, supports:

TagNameValues
36NewSeqNothe new sequence number
123GapFillFlagY=gap fill (replay the gap from store), N=hard reset

This message is available in the codec but not automatically triggered by the acceptor. It is intended for administrative use during recovery scenarios.

Sequence Numbers

Each FIX session maintains two independent sequence number streams:

StreamSourceTracker
Inboundtag 34 on client messagesFixSession::last_seq_num_in (starts at 1)
Outboundtag 34 on server messagesArc<AtomicU64> incremented atomically per message

Gap Detection

On each inbound message, the server compares msg_seq_num against last_seq_num_in:

  1. msg_seq_num > last_seq_num_in — A gap is detected. The server sends a ResendRequest (35=2) with BeginSeqNo = last_seq_num_in and EndSeqNo = 0. The message with the out-of-sequence number is discarded.
  2. msg_seq_num == last_seq_num_in or msg_seq_num < last_seq_num_in — The message is accepted. last_seq_num_in is advanced to msg_seq_num + 1.

The outbound sequence number is incremented atomically (fetch_add(1, SeqCst)) on every message sent by the server — ExecutionReports, heartbeats, MD snapshots, session control messages, and resend replays all consume a sequence number.

Message Store

The MessageStore is a file-backed append-only journal that persists outbound messages for ResendRequest replay.

Format

Each session’s store is a file at <store_dir>/<sender_comp_id>-<target_comp_id>.fixlog. The file is newline-delimited JSON:

{"last_seq_in":0,"last_seq_out":5}
{"seq":1,"msg":"8=FIX.4.2\x019=...\x0135=0\x01..."}
{"seq":2,"msg":"8=FIX.4.2\x019=...\x0135=8\x01..."}
  • Line 1: StoreHeader — last_seq_in and last_seq_out counters, persisted on every mutation.
  • Lines 2+: MessageEntry — one per outbound message, with sequence number and full FIX wire string.

Initialization

The store is lazily initialized on the first successful logon message received after the session is connected. It is loaded from disk if the .fixlog file exists (recovering prior last_seq_in/last_seq_out and reloading the latest messages up to cap entries). If the file does not exist, a fresh store is created.

Capacity

The in-memory outbound buffer is capped at store_cap entries (default 1000). When the cap is exceeded, the oldest entry is evicted from memory. The on-disk journal retains all messages for the session’s lifetime.

Replay

record_outbound adds a message to both the in-memory VecDeque and the on-disk journal file. replay(from_seq, to_seq) returns messages where seq >= from_seq and (if to_seq > 0) seq < to_seq. A to_seq of 0 means “unbounded.”

Network Considerations

  • The listener binds to all interfaces by default (0.0.0.0). For production, restrict to a specific interface or place behind a reverse proxy.
  • No TLS is provided at the FIX layer. Use a VPN or stunnel for encrypted transport.
  • There is no explicit max_connections limit; the acceptor spawns a task per connection. Use OS-level limits (ulimit -n) or a connection-counting gauge to manage resource consumption.
