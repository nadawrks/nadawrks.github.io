NadaTrade Documentation

Simulation

NadaTrade’s clock and latency layer controls how time advances, how network latency is modeled, and how test scenarios are injected. It is the backbone for testing, bot development, and production rehearsal.

Overview

The simulation subsystem lives in crates/nadatrade-simulation/ and provides four capabilities:

ComponentRole
SimClockSource of truth for all business-logic time
ClockDriverEmits periodic ClockTick commands to drive the event loop
LatencySimulatorAdds realistic per-participant command delays
ScenarioInjectorInjects 7 types of synthetic events into the system

All business code reads time from SimClock::now(). Direct calls to chrono::Utc::now(), tokio::time::sleep, or Instant::now in business logic are forbidden (only allowed in gateway heartbeats, metrics, DB batching, and the sim subsystem itself).

Clock Modes

NadaTrade supports three clock modes, selected via [simulation] config:

[simulation]
mode = "realtime"      # or "accelerated" or "replay"

RealTime Mode

1:1 mapping to wall clock. Every wall second equals one simulation second.

[simulation]
mode = "realtime"

The RealTimeClock returns Utc::now() and reports wall_per_sim_sec() == 1s. The ClockDriver sleeps exactly one wall second between each ClockTick. This mode is ideal for live bot development, FIX/WS integration testing, and observing session transitions in real time.

Accelerated Mode

Simulation time runs faster than wall clock by a configurable factor.

[simulation]
mode = "accelerated"
clock_speed = 60.0     # 1 wall second = 60 sim seconds (1 minute)

The AcceleratedClock tracks a wall Instant at construction, then multiplies elapsed wall milliseconds by clock_speed to compute simulation time:

sim_time = sim_start + (wall_elapsed_ms × clock_speed)

wall_per_sim_sec() returns 1000 / clock_speed ms, so the ClockDriver ticks every 1000/60 ≈ 17ms when clock_speed = 60. Higher factors mean faster simulation.

Pause / Resume

The AcceleratedClock can pause and resume. When paused, now() returns the time at the moment of pause. Useful for inspecting state mid-backtest.

# via OrderCommand (sent from TUI or API)
OrderCommand::Scenario { event: ScenarioEvent::BroadcastSystemMessage { ... } }

When speed changes, a ClockSpeedChanged exchange event is emitted with the new factor.

Replay Mode

Driven by an NDJSON feed file. Each record in the feed sets the simulation clock to its sim_time and then the system processes the next event.

[simulation]
mode = "replay"
replay_feed = "/data/feed.ndjson"
sim_start = "2024-01-02T09:30:00-05:00"

Feed Format

The NDJSON feed contains one JSON object per line. Two record types are supported:

Trade records:

{"sim_time":"2024-01-15T10:00:00.123Z","instrument":"PETR4","type":"trade","price":"38.42","qty":"1000","aggressor_side":"buy"}

Quote records:

{"sim_time":"2024-01-15T10:00:01Z","instrument":"PETR4","type":"quote","bid":"38.40","bid_qty":"5000","ask":"38.45","ask_qty":"3000"}

Fields:

FieldTradeQuoteDescription
sim_timeYesYesISO-8601 timestamp (sets the clock)
instrumentYesYesInstrument ID (must match registry)
typeYesYes"trade" or "quote"
priceYes—Trade price (string)
qtyYes—Trade quantity (string)
aggressor_sideYes—"buy" or "sell"
bid—YesBid price (string)
bid_qty—YesBid quantity (string)
ask—YesAsk price (string)
ask_qty—YesAsk quantity (string)

Replay Behavior

The MarketReplay::from_ndjson() parser reads all lines on startup. Records iterate in order via next_record(). Each record:

  1. Sets the ReplayDrivenClock time to record.sim_time
  2. Sends OrderCommand::ClockTick { sim_time } down the command channel
  3. The engine processes the tick (drives session state machine, triggers scheduled actions)

The feed reader inserts a 1ms sleep between records to allow the event loop to process. This is not pacing — it’s simply yielding to the async runtime.

replay_pacing (planned): when true, the feed reader waits for wall clock to align with record timestamps, creating realistic gaps. When false (current default), records are processed as fast as the 1ms yield allows.

sim_start overrides the feed’s initial timestamp. If omitted, the clock starts at the timestamp of the first record in the feed.

Use the replay-convert tool in tools/replay-convert/ to convert B3, NYSE, or Binance historical data to NDJSON:

ClockDriver

ClockDriver is the bridge between a SimClock and the command channel. It runs as an async task:

  1. Queries clock.wall_per_sim_sec() to get the sleep duration
  2. Sleeps for that duration
  3. Reads clock.now() for the current sim time
  4. Sends OrderCommand::ClockTick { sim_time } to the command channel
  5. Repeats
#![allow(unused)]
fn main() {
// Simplified: ClockDriver::run()
loop {
    if let Some(wall_dur) = self.clock.wall_per_sim_sec() {
        tokio::time::sleep(wall_dur).await;
    }
    let now = self.clock.now();
    cmd_tx.send(OrderCommand::ClockTick { sim_time: now }).await?;
}
}

In RealTime mode, this fires every 1 wall second. In Accelerated mode, it fires every 1000/clock_speed ms. In Replay mode, the ClockDriver is not used — the feed reader task sends ticks directly.

Latency Simulation

The LatencySimulator sits between gateways and the matching engine, inserting realistic per-participant delays on incoming orders.

Channel Pipeline

Gateway → LatencySimulator → PreTrade → MatchingEngine

When latency_seed is set in config, the run_latency_middleware task intercepts every OrderCommand from the gateway channel. It looks up the participant’s latency profile, computes a delay, and sleeps before forwarding the command.

If latency_seed is absent, a pass-through task forwards commands with zero delay.

Latency Profiles

Five built-in profiles are available, configured per participant in their TOML file:

ProfileMean DelayStd DevSamplingDescription
"none"0 µs—FixedNo delay (default)
{ fixed = { micros = N } }N µs0FixedExact fixed delay
"co_location"50 µs10 µsNormalExchange colocation
"remote"5,000 µs1,500 µsNormalSatellite/remote
{ normal = { mean_us = M, stddev_us = S } }M µsS µsNormalCustom profile

Box-Muller Sampling

Profiles using normal distribution use the Box-Muller transform for realistic delay variation:

#![allow(unused)]
fn main() {
let z = (-2.0 * u.ln()).sqrt() * (2.0 * PI * v).cos();
mean + stddev * z
}

Results are clamped to zero (no negative delays). The underlying RNG is a seeded StdRng, so latency_seed = 42 produces the same delay sequence every run.

Configuring Latency per Participant

In a participant TOML file:

[participants.super_bot]
comp_id = "SUPER_BOT"
display_name = "Super Trading Bot"
initial_cash = { USD = "1000000.00" }

# Latency profile examples (choose one):
latency_profile = "none"                    # No delay
latency_profile = "co_location"            # ~50µs normal delay
latency_profile = "remote"                 # ~5000µs normal delay
latency_profile = { fixed = { micros = 250 } }  # Exactly 250µs
latency_profile = { normal = { mean_us = 500, stddev_us = 100 } }  # Custom

The default profile is "none", simulating a participant with zero network latency.

Market Data Staggering

In addition to command latency, each participant can experience staggered market data arrival via the md_extra_delay_us field:

[participants.slow_broker]
comp_id = "SLOW_BROKER"
latency_profile = "co_location"
md_extra_delay_us = 750   # Additional 750µs before MD messages arrive

How It Works

  1. The LatencySimulator::md_delay_for() method computes the per-participant MD delay
  2. md_extra_delay_us always takes priority when set — it overrides any derived value from the latency profile
  3. When md_extra_delay_us is absent, the delay is derived from the profile:
    • None → 0 µs
    • CoLocation → 50 µs
    • Remote → 5,000 µs
    • Fixed { micros } → that exact value
    • Normal { mean_us, .. } → the mean value
  4. The delay is applied in both the FIX acceptor (before dispatching market data messages to a FIX session) and the WS server (before sending market data frames to a WebSocket client)

This creates realistic staggered arrival of market data updates across participants, even when the market data itself is generated simultaneously by the matching engine.

Scenario Injection

Seven scenario types can be injected at runtime via OrderCommand::Scenario, enabling testing of market events, regulatory actions, and infrastructure failures without disrupting live data.

Scenario Types

#VariantEffect
1haltPlaces an instrument into TradingHalt. Optional duration_secs for auto-resume; without it, manual resume is required.
2resumeForces an instrument back to ContinuousTrading from any halted state.
3set_reference_priceOverrides the reference price used by circuit breakers and auction uncrossing.
4trigger_circuit_breakerImmediately triggers a circuit breaker halt for the instrument.
5expire_gtcExpires all GTC orders for the instrument at the current sim time.
6delist_instrumentRemoves an instrument from trading entirely, with a reason string.
7broadcastSends a BroadcastSystemMessage event with arbitrary text.

Via WebSocket / API

Scenarios travel as OrderCommand::Scenario through the same command channel as orders. The WS server routes them:

{
  "type": "scenario",

      "duration_secs": 300,

When a scenario is processed by the engine, a ScenarioApplied exchange event is emitted, containing the original ScenarioEvent wrapped for observability.

# latency_seed omitted → no latency middleware → direct pass-through

Determinism & Reproducibility

  • Same seed, same results. With latency_seed = N, the Box-Muller RNG produces identical delay sequences across runs. Feed records always iterate in order.
  • No RNG in matching core. The matching engine is fully deterministic. Latency simulation is the only source of stochasticity.
  • BTreeMap for ordering. Hot-path collections use BTreeMap, not HashMap, guaranteeing deterministic iteration order.
  • Replay identical. Running the same feed file twice with the same latency_seed produces identical trade outcomes — critical for backtest validation and regression testing.
