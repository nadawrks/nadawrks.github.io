NadaTrade Documentation

Matching Engine

NadaTrade runs one independent matching engine per instrument, each owning a central limit order book (CLOB). The engine processes OrderCommand variants — New, Cancel, Replace, ClockTick, SessionTransition, Scenario, and Status — and emits ExchangeEvent variants back to the system.

1. Architecture overview

Each MatchingEngine is keyed by InstrumentId (the instrument name string). The OrderRouter (crates/nadatrade-matching/src/router.rs) dispatches incoming commands to the correct engine via a HashMap<InstrumentId, MatchingEngine>.

The CLOB itself (Clob struct in clob.rs:17–25) uses deterministic data structures throughout:

#![allow(unused)]
fn main() {
pub struct Clob {
    pub bids: BTreeMap<Price, VecDeque<RestingOrder>>,
    pub asks: BTreeMap<Price, VecDeque<RestingOrder>>,
    by_order_id: HashMap<OrderId, (Price, Side)>,
    pub by_client_id: HashMap<(ParticipantId, String), OrderId>,
    pub last_trade_price: Option<Price>,
    pub stop_book: StopBook,
    pub expiries: BTreeMap<DateTime<Utc>, Vec<OrderId>>,
}
}
  • BTreeMap<Price, ...> — price levels are ordered. Bids iterate descending (best = highest, via .last_key_value()). Asks iterate ascending (best = lowest, via .first_key_value()). This guarantees deterministic price-level iteration.
  • VecDeque<RestingOrder> — within each price level, orders are FIFO (price-time priority). New orders .push_back(), fills .pop_front().
  • by_order_id — O(1) lookup for cancels and replaces.
  • by_client_id — O(1) duplicate ClOrdID detection, keyed on (participant, client_order_id).
  • No HashMap iteration in hot paths — matching walks BTreeMap entries only.

2. Order types

NadaTrade supports six order types (OrderType enum, enums.rs:13–20):

OrderTypeDescription
MarketFills immediately at the best available opposite price. Must not specify price, stop_price, or display_qty. Requires Ioc, Fok, or Day TIF. If the opposite book is empty → OrderRejected(MarketOrderNoLiquidity).
LimitRests at a specified price (must be present and a multiple of tick_size). Supports all 7 TIF variants.
StopParks in the Stop Book with a trigger_price. When the market crosses the trigger (bid rises above for buys, ask falls below for sells), the order triggers and becomes a Market order (engine.rs:457). Requires stop_price; must not have price. TIF: Day, Gtc, Gtd.
StopLimitLike Stop but triggers into a Limit order at the specified price. Requires both price and stop_price. TIF: Day, Gtc, Gtd.
MarketToLimitLike Market but after filling what it can, the unfilled remainder rests as a Limit at the last trade price (engine.rs:836). Must not specify price or stop_price. TIF: Day, Ioc.
IcebergDisplays only display_qty on the order book; the rest (qty − display_qty) is in a hidden reserve. When the visible portion is exhausted, it replenishes from the hidden reserve and re-enters at the back of the price queue (loses time priority). Requires price and a valid display_qty (must be > 0 and ≤ qty). TIF: Day, Gtc, Gtd.

Market/MarketToLimit vs empty book

Both Market and MarketToLimit are rejected immediately if the opposite side has no resting orders (clob.rs:132–143).

Field validation per order type

validate_tif() also checks required/optional fields (tif_matrix.rs:49–96):

  • Limit: requires price; rejects stop_price and display_qty.
  • Market: rejects all of price, stop_price, and display_qty.
  • Stop: requires stop_price; rejects price.
  • StopLimit: requires both price and stop_price.
  • MarketToLimit: rejects all of price, stop_price, and display_qty.
  • Iceberg: requires price and display_qty where display_qty > 0 and display_qty ≤ qty.

4. Order lifecycle

All orders follow this state machine:

   ┌──────────────────────────────────────────────────────┐
   │                                                      │
   ▼                                                      │
  New ──► Accepted ──► (Partial Fill ──► Accepted ──► ...) ──► Filled
   │                       │                                   ▲
   │                       │                                   │
   └──► Rejected           └──► Cancelled                      │
   └──► Expired            └──► Expired                        │
  • New → Accepted: Order passes session gating, TIF validation, lot size, min/max qty, price tick size, and price band checks. OrderAccepted event emitted.
  • New → Rejected: Fails any defence-in-depth check. OrderRejected event emitted with a specific RejectReason.
  • New → Expired: Market order hits empty book, FOK unfeasible. OrderExpired emitted.
  • Accepted → Partial Fill: On each trade, OrderPartiallyFilled events are emitted for both the resting order (aggressor=false) and the incoming order (aggressor=true).
  • Accepted → Filled: When remaining_qty reaches zero. OrderFilled emitted.
  • Accepted → Cancelled: Client cancel request, STP, session end, scenario, or instrument delisting.
  • Accepted → Expired: IOC unfilled remainder, FOK not feasible, GTD time reached, AtOpen/AtClose unfilled in auction, Day order at EOD with GTC EOD purge.

5. Price-time priority

The CLOB enforces strict price-time priority (clob.rs):

  1. Best price first: Bids are matched from highest to lowest price. Asks are matched from lowest to highest.
  2. FIFO within a price level: Orders at the same price are matched in insertion order via VecDeque. pop_front() takes the oldest order.
  3. New resting orders enter at the back: push_back() — they yield to all existing orders at that price.
  4. Partial fills keep position: A partially filled order (with remaining display_qty > 0) is pushed back to the front of the queue via push_front() (clob.rs:371), preserving its time priority over orders that came later.
  5. Iceberg replenishment loses priority: When an iceberg’s visible portion is exhausted and it replenishes from hidden reserves, it is pushed to the back (clob.rs:369), yielding to all other orders at that level.

6. Self-Trade Prevention (STP)

STP prevents a participant from trading against their own resting orders. The StpMode enum (enums.rs:48–55) has four variants, configured per-order via the stp_mode field:

CancelAggressive (StpMode::CancelAggressive)

The resting order is put back at the front of its price queue (retains time priority via push_front). The aggressive (incoming) order is cancelled. If no prior fills occurred in this matching cycle, an OrderRejected(StpCancelled) is emitted. If there were prior fills, an OrderCancelled(StpCancelAggressive) is emitted (clob.rs:205–228).

CancelResting (StpMode::CancelResting)

The resting order is removed from the book and cancelled with OrderCancelled(StpCancelResting). The aggressive order continues matching against other resting orders (clob.rs:229–244).

CancelBoth (StpMode::CancelBoth)

Both orders are cancelled. The resting order emits OrderCancelled(StpCancelBoth). The incoming order emits OrderCancelled(StpCancelBoth) if there were prior fills, or OrderRejected(StpCancelled) if no fills occurred (clob.rs:245–288).

None (StpMode::None)

No STP check. Orders from the same participant can match — this is allowed for market makers who run separate trading bots under one participant ID.

7. Stop orders

Stop orders rest in the StopBook (stop_book.rs:12–15), not in the CLOB:

#![allow(unused)]
fn main() {
pub struct StopBook {
    pub buy_stops: BTreeMap<Price, VecDeque<StopOrder>>,
    pub sell_stops: BTreeMap<Price, VecDeque<StopOrder>>,
    pub by_order_id: HashMap<OrderId, (Price, bool)>,
}
}

Each StopOrder bundles a RestingOrder with its trigger_price.

Trigger conditions

Scanned after every trade via stop_book.scan(last_trade_price) (stop_book.rs:60–87):

SideTriggers when
Buy stoplast_trade_price >= trigger_price (market rises to or above the stop)
Sell stoplast_trade_price <= trigger_price (market falls to or below the stop)

Scan uses BTreeMap range queries: buy_stops.range(..=last_trade) returns all buy stops with trigger ≤ last trade, ascending by trigger price. sell_stops.range(last_trade..) returns all sell stops with trigger ≥ last trade, descending by trigger price.

Triggered behaviour

When triggered (engine.rs:456–460):

  • Stop → converts to OrderType::Market (no limit price).
  • StopLimit → converts to OrderType::Limit with the order’s price field as the limit.

The triggered order is then passed to clob.match_order() with the converted type.

Stop cascade

Stop execution uses a breadth-first cascade queue (engine.rs:446–482):

  1. Initial scan of the Stop Book against last_trade_price.
  2. All triggered orders are added to a VecDeque.
  3. Each order is popped, matched, and emitted. Each match may update last_trade_price.
  4. After each individual stop-order match, a fresh scan of the Stop Book is run. Newly triggered orders are appended to the back of the queue.
  5. This repeats until the queue is empty — stops can cascade: one stop’s fill triggers another stop, and so on.

After the stop cascade, the circuit breaker check runs (see Circuit breaker).

GTD stop expiry

GTD stop orders are expired on ClockTick by scanning both buy_stops and sell_stops for orders whose Gtd(expiry) time has been reached or passed (engine.rs:142–174).

Day stop EOD cleanup

On session close, cancel_all_stop_day_orders() (clob.rs:540–558) partitions each stop-book price level: Day orders are removed, non-Day orders are retained. The removed Day orders emit OrderCancelled(SessionEnd).

8. Iceberg orders

Iceberg orders display only a fraction of their total quantity on the order book. The RestingOrder struct tracks this through four fields (resting_order.rs:14–18):

FieldMeaning
original_qtyTotal quantity at order entry. Used in replace logic.
remaining_qtyTotal unfilled quantity (visible + hidden).
display_qtyCurrently visible quantity on the book.
hidden_qtyRemaining hidden reserve.
original_displayThe initial display_qty cap; used to bound replenishments.

During matching (clob.rs:294)

A fill consumes fill_qty = min(incoming_remaining, resting.display_qty). Both remaining_qty and display_qty are reduced by fill_qty. Only the visible portion is matched against — the hidden reserve is invisible to aggressors.

Replenishment (resting_order.rs:39–49)

When display_qty drops to zero but hidden_qty > 0:

  1. iceberg_replenish() refills display_qty to min(original_display, hidden_qty).
  2. The replenished order is push_back() into its price level — loses time priority (clob.rs:369).
  3. Returns the replenished amount so the caller can track the new visible size.

Non-replenished (partial fill, display still > 0)

If display_qty is still positive after the fill (partial fill of the visible portion only), the order is push_front() — retains time priority (clob.rs:371).

FOK and iceberg visibility

The FOK feasibility check (clob.rs:414–443) counts remaining_qty (total, including hidden), not just display_qty. A FOK order can succeed against an iceberg even if the visible portion alone would be insufficient.

9. FOK (Fill-or-Kill)

FOK orders must fill in their entirety against the current order book, or fail entirely with no partial fills and no resting remainder.

Feasibility pre-check (clob.rs:414–443)

Before matching begins, fok_feasible() walks the opposite book at all acceptable prices (respecting limit price constraints) and sums remaining_qty across all resting orders. It counts the full quantity, including iceberg hidden reserves.

If the total available quantity at acceptable prices is less than the FOK order’s quantity → OrderExpired(FokNotFilled) is emitted immediately, with no TradePrinted events generated at all.

If feasible, the FOK proceeds through the normal matching loop. Since the feasibility check guarantees sufficient quantity exists, the FOK is guaranteed to fully fill — no remainder handling is needed.

10. IOC (Immediate-or-Cancel)

IOC orders fill whatever is possible against the current book, then cancel the remainder.

Matching proceeds normally through the loop in clob.match_order(). After all possible fills, if remaining_qty > 0:

  • If the order is Ioc or Fok, or the order type is Market → the unfilled remainder emits OrderExpired(IocNotFilled) (engine.rs:822–832).
  • This also applies to Market + Day orders: after matching, any unfilled portion is treated as IOC-like and expired.
  • MarketToLimit + Day orders: after matching, the unfilled portion rests as a Limit order at the last trade price (or zero if no trade occurred) rather than expiring.

11. Replace semantics

Order replacement (engine.rs:945–1178) first removes the existing order from the CLOB by its (participant, orig_client_id) key, then processes a new order.

Validation checks

Before replacement proceeds:

  • Session must accept cancels (Trading, PreOpen, auction states — not Closed or TradingHalt).
  • Target order must exist (by orig_client_id) → else CancelRejected(UnknownOrder).
  • new_client_id must not collide with an existing order from the same participant → else CancelRejected(DuplicateClOrdId).
  • new_qty must not be less than the quantity already filled → else CancelRejected(InvalidReplaceParams).

Decrease-only: keeps priority (engine.rs:1019–1049)

When both conditions are true:

  • new_qty ≤ original_qty (quantity not increased)
  • new_price == existing.price (price unchanged)

The order is modified in-place:

original_qty = new_qty
remaining_qty = new_qty - filled_qty

The order is reinserted into the book via clob.insert() which does push_back(), but since this is a decrease only (qty reduced, price same), it retains its position. No new matching is performed — the order just updates its size. An OrderReplaced event is emitted.

Price change or quantity increase: loses priority (engine.rs:1052–1178)

When either condition is true:

  • new_qty > original_qty (quantity increased)
  • new_price != existing.price (any price change, better or worse)

The old order is removed, an OrderReplaced event is emitted, then the order re-enters as a new order:

  1. match_order() is called with the new quantity and price.
  2. The replacement order gets a new OrderId (fields.id).
  3. Any fills against the current book happen immediately.
  4. If unfilled, the remainder rests as a new order at the back of the queue (clob.insert → push_back).
  5. After matching, the stop cascade and circuit breaker checks run on the new trades.

12. Circuit breaker

The circuit breaker (engine.rs:484–506) triggers when the last trade price deviates too far from the reference price.

Trigger condition

|last_trade − ref_price| / ref_price > price_band

Where:

  • ref_price is the instrument’s reference_price (set via config, auction, or scenario).
  • price_band is the instrument’s price_band (e.g. 0.10 = 10%).

If ref_price == 0, price_band == 0, or last_trade_price is None, the check is skipped.

On trigger

  • The session is forced into SessionState::TradingHalt { reason: CircuitBreaker, until: sim_time + halt_duration_secs }.
  • In this state, all new orders are rejected with RejectReason::InstrumentHalted and all cancels/replaces are rejected too.
  • After halt_duration_secs elapses on a ClockTick, the session transitions to ReopeningAuction, then to Trading.

When checked

The circuit breaker check runs as part of run_stop_cascade_and_circuit_breaker(), which is called:

  • After every process_new match cycle.
  • After every process_replace match cycle.

The stop cascade runs first (so all stop triggers from a trade are processed), then the CB check evaluates the final last_trade_price.

13. Auction

Auction scheduled states

The session state machine drives auctions. On transition from an auction to Trading (or Closed), run_auction_uncross() fires:

TransitionAuction type
OpeningAuction → TradingAuctionType::Opening
ReopeningAuction → TradingAuctionType::Reopening
ClosingAuction → ClosedAuctionType::Closing

Call market algorithm (auction.rs:27–253)

The uncross algorithm proceeds in three tie-break rounds:

Round 0 — Find candidates: For every price level present in either side of the book, compute:

  • buy_demand = sum of all bid quantities at prices ≥ candidate.
  • sell_supply = sum of all ask quantities at prices ≤ candidate.
  • volume = min(buy_demand, sell_supply).
  • surplus = buy_demand − sell_supply.

Tie-break 1 — Maximize volume: Retain only the candidates with the largest volume.

Tie-break 2 — Minimize absolute surplus + market pressure: Retain candidates with the smallest |surplus|.

  • If all remaining candidates have surplus > 0 (buy pressure) → keep only the highest price.
  • If all remaining candidates have surplus < 0 (sell pressure) → keep only the lowest price.

Tie-break 3 — Reference price proximity: Sort remaining candidates by proximity to reference_price. If tied, prefer the higher price.

The first candidate is the clearing price.

Trade allocation (auction.rs:292–358)

Orders are collected in priority order:

  • Bids: descending price (highest first). Within a price level, FIFO.
  • Asks: ascending price (lowest first). Within a price level, FIFO.

A simplified two-phase allocation fills orders in priority order up to the traded_qty cap. Buy fills and sell fills are paired to produce TradePrinted events.

Post-uncross

  • A ReferencePriceChanged event is emitted (source: Auction), updating the reference price to the clearing price.
  • An AuctionUncrossed event is emitted with the clearing price, traded quantity, imbalance quantity, and imbalance side.
  • AtOpen/AtClose orders that were not fully filled emit OrderExpired(AuctionUnfilled).
  • The CLOB is updated: filled orders are reduced or removed, unfilled auction-TIF orders are removed.
  • After applying auction events, the stop cascade and circuit breaker are run.

14. End-of-Day cleanup

When the session transitions to SessionState::Closed (either via ClockTick or SessionTransition), the engine executes three cleanup operations (engine.rs:129–136):

1. Cancel all Day orders on the CLOB

clob.cancel_all_day_orders() (clob.rs:508–537) scans both bids and asks, collects all orders with tif == Day, removes them via remove_by_id(), and emits OrderCancelled(SessionEnd) for each.

2. Cancel all Day orders in the Stop Book

clob.cancel_all_stop_day_orders() (clob.rs:540–558) partitions each stop-book price level, removing Day orders while retaining non-Day orders. Emits OrderCancelled(SessionEnd).

3. Expire GTC orders (per-participant EOD purge)

expire_eod_gtc() (engine.rs:382–420) scans both books for GTC orders belonging to participants listed in eod_purge_participants. Each matching order emits OrderExpired(DayEndGtc). If eod_purge_participants is empty, this step is skipped.

Additionally, GTD order expiry runs on every ClockTick regardless of session state (engine.rs:139).
