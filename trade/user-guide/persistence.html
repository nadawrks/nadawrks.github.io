NadaTrade Documentation

Persistence

NadaTrade uses an event sourcing persistence model backed by PostgreSQL. There is no mutable “current state” database. All system state is reconstructed from two tables: an append-only event log and periodic CLOB snapshots. This foundation enables full auditability and deterministic replay.

Tables

NadaTrade creates five tables on first start (via sqlx::migrate!):

TablePurpose
eventsAppend-only event log, partitioned monthly on occurred_at
snapshotsPeriodic full serializations of engine state per instrument
book_snapshotsLegacy table — superseded by snapshots
ledger_snapshotsParticipant position snapshots
persist_metaKey-value metadata (last persisted sequence, etc.)

Events table

The events table is the authoritative record of everything that happened in the system. It is append-only — rows are never updated or deleted.

CREATE TABLE events (
    sequence       BIGINT       NOT NULL,
    occurred_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    sim_time       TIMESTAMPTZ  NOT NULL,
    instrument_id  TEXT,
    participant_id TEXT,
    event_type     TEXT         NOT NULL,
    payload        JSONB        NOT NULL,
    PRIMARY KEY (occurred_at, sequence)
) PARTITION BY RANGE (occurred_at);

Columns:

  • sequence — globally unique, monotonically increasing event number. Assigned by the binary at fan-out time.
  • occurred_at — wall-clock time the event was persisted (PostgreSQL server clock).
  • sim_time — simulation time extracted from the event. This is the authoritative business time regardless of clock mode (RealTime, Accelerated, or Replay).
  • instrument_id — the instrument this event pertains to, or NULL for system-wide events (SystemMessage, ClockSpeedChanged, etc.).
  • participant_id — the participant who originated this event, or NULL for book/session/system events.
  • event_type — snake_case variant name: order_accepted, order_rejected, order_filled, order_partially_filled, order_cancelled, order_expired, order_replaced, cancel_rejected, trade_printed, book_updated, session_state_changed, auction_uncrossed, reference_price_changed, obligation_settled, scenario_applied, clock_speed_changed, replay_started, replay_stopped, system_message.
  • payload — the full serialized ExchangeEvent as JSONB.

Indexes:

CREATE INDEX idx_events_seq         ON events (sequence);
CREATE INDEX idx_events_instr_seq   ON events (instrument_id, sequence);
CREATE INDEX idx_events_type        ON events (event_type, sequence);
CREATE INDEX idx_events_part_seq    ON events (participant_id, sequence) WHERE participant_id IS NOT NULL;

Partitioning

The events table uses monthly range partitioning on occurred_at. Child partitions are named events_yYYYYMM:

events
├── events_y202606  (2026-06-01 to 2026-07-01)
├── events_y202607  (2026-07-01 to 2026-08-01)
└── ...

Partitions are created lazily — on the first flush into a new month, ensure_current_partition() issues CREATE TABLE IF NOT EXISTS events_yYYYYMM PARTITION OF events FOR VALUES FROM (...) . The current month is cached in last_partition_month so the partition check runs at most once per month, not on every flush.

Querying

The partition key (occurred_at) is in the primary key, so range scans on wall-clock time use partition pruning automatically. To query by simulation time or event type, combine with the corresponding indexes:

SELECT * FROM events
WHERE sim_time BETWEEN '2026-06-01' AND '2026-06-02'
ORDER BY sequence;

Snapshots table

Replaying every event since system start to recover current state would be prohibitively slow. The snapshots table stores periodic full serializations of engine state for each instrument:

CREATE TABLE snapshots (
    instrument_id   TEXT        NOT NULL,
    snapshot_at     TIMESTAMPTZ NOT NULL,
    sequence        BIGINT      NOT NULL,
    session_state   JSONB       NOT NULL,
    clob_state      JSONB       NOT NULL,
    stop_book_state JSONB       NOT NULL,
    expiries_state  JSONB       NOT NULL,
    state           JSONB       NOT NULL,
    PRIMARY KEY (instrument_id, snapshot_at)
);

Each row captures the complete engine state at a point in time:

  • session_state — the session state machine state (Closed, PreOpening, OpeningAuction, Trading, ClosingAuction, Closed, TradingHalt, ReopeningAuction).
  • clob_state — full order book: bids and asks as BTreeMap<Price, VecDeque<RestingOrder>>.
  • stop_book_state — stop order book (untriggered stop and stop-limit orders).
  • expiries_state — pending GTD (Good-Till-Date) expiry queue.
  • state — engine-level auxiliary state.
  • sequence — the global sequence number this snapshot corresponds to.

Index:

CREATE INDEX idx_snapshots_instr_seq ON snapshots (instrument_id, sequence);

Snapshot pruning

Each time a new snapshot is written for an instrument, NadaTrade prunes older entries for that instrument, retaining only the most recent 3 snapshots. This prevents unbounded growth in the snapshots table while ensuring enough history for diagnostic purposes.

EventWriter

The EventWriter is the core persistence actor. It lives behind an Arc<Mutex<EventWriter>> and is called from the main event fan-out loop.

Buffering and flush

Events are buffered in memory until one of two thresholds triggers a flush:

  1. Batch size — when buffer.len() >= batch_max, the writer flushes immediately after write().
  2. Wall-clock timer — a periodic flush runs at batch_max_ms interval, ensuring events are persisted even at low throughput.

Both thresholds are configurable. Whichever triggers first executes the flush.

During a flush, the writer:

  1. Checks if we’ve entered a new month — calls ensure_current_partition() to create the next monthly partition if needed.
  2. Takes the buffered events (leaving an empty buffer behind).
  3. Opens a PostgreSQL transaction.
  4. Inserts each event row with INSERT INTO events ....
  5. Updates persist_meta with key = 'last_sequence' → the highest-sequence event in this batch, using ON CONFLICT ... DO UPDATE.
  6. Commits the transaction.

All events in a batch are committed atomically. If any insert fails, the entire batch is rolled back and the error is returned.

Metrics

The writer exports Prometheus metrics:

MetricTypeDescription
nadatrade_persist_queue_depthGaugeNumber of events buffered waiting for flush
nadatrade_persist_batch_flush_msHistogramWall-clock duration of each flush transaction

Noop mode

When no database URL is configured, EventWriter::new_noop() is used. Events are still buffered and flush clears the buffer, but no database calls are made. This is useful for development, testing, or when persistence is intentionally disabled.

Snapshots

Auto-snapshot triggering

The main event loop monitors per-instrument event counters via EventWriter::should_snapshot(instrument, threshold). When the counter reaches snapshot_every_events (default: 10,000), the engine serializes its state via serialize_snapshot(global_seq) and the writer persists it to the snapshots table.

The counter is per-instrument — tracked in events_since_snapshot: HashMap<String, u64> and incremented on every event that has an instrument_id. After a snapshot is written, the counter is reset to zero via reset_snapshot_count().

The EngineSnapshot struct contains:

#![allow(unused)]
fn main() {
pub struct EngineSnapshot {
    pub sequence: u64,
    pub session_state: serde_json::Value,
    pub clob_state: serde_json::Value,
    pub stop_book_state: serde_json::Value,
    pub expiries_state: serde_json::Value,
    pub state: serde_json::Value,
}
}

Each component is a serde_json::Value — the engine serializes its internal BTreeMap-based state to JSON. On recovery, these are deserialized back into the engine’s native structures.

Recovery flow

On restart, the system reconstructs state through load_recovery_data():

  1. Read persist_meta — query SELECT value FROM persist_meta WHERE key = 'last_sequence' to find the last persisted sequence number. If 0, this is a fresh database — return empty state.

  2. Load newest snapshots — for each instrument, query the most recent snapshot (highest snapshot_at) using SELECT DISTINCT ON (instrument_id) ... ORDER BY instrument_id, snapshot_at DESC. Each snapshot includes the sequence number it was taken at.

  3. Load events since snapshot — find the minimum snapshot sequence across all instruments (min_seq). Query SELECT sequence, payload FROM events WHERE sequence > min_seq ORDER BY sequence ASC. If no snapshots exist, all events are loaded.

  4. Replay events — events are deserialized from JSONB and replayed through the matching engine in sequence order. The engine applies each event, rebuilding the CLOB, stop book, session state, and expiry queues. After replay, the engine is ready to accept new orders.

The recovery data is returned as RecoveryState:

#![allow(unused)]
fn main() {
pub struct RecoveryState {
    pub last_sequence: u64,
    pub instrument_states: HashMap<String, (u64, serde_json::Value)>,
    pub events: Vec<(u64, serde_json::Value)>,
}
}

Recovery with snapshots (fast path)

If snapshots exist:

  • Each engine is initialized from its snapshot state (deserialized JSON → native structures).
  • Only events after the snapshot sequence are replayed.
  • Typical recovery time: seconds, even with millions of historical events.

Recovery without snapshots (slow path)

If no snapshots exist (fresh install, or snapshots were deleted):

  • Engines start empty.
  • All events from the events table are replayed sequentially.
  • Recovery time scales linearly with event count. For systems with hundreds of millions of events, configure snapshot frequency appropriately.

Configuration

All persistence settings live under [persist] in the config file:

[database]
url = "postgres://user:pass@localhost/nadatrade"
max_connections = 8

[persist]
batch_max = 500
batch_max_ms = 50
snapshot_every_events = 10000
queue_warn_depth = 5000
KeyDefaultDescription
[database].urlNonePostgreSQL connection string. If absent, persistence runs in noop mode.
[database].max_connections8Connection pool size passed to sqlx::PgPool.
persist.batch_max500Maximum events buffered before an automatic flush.
persist.batch_max_ms50Maximum wall-clock milliseconds between periodic flushes.
persist.snapshot_every_events10000Per-instrument event count threshold for auto-snapshot.
persist.queue_warn_depth5000Queue depth at which a warning is logged (monitoring).

Tuning guide

  • High-throughput trading — increase batch_max (1000–2000) to reduce transaction overhead. Consider raising snapshot_every_events (50,000–100,000) to avoid snapshot writes during peak activity.
  • Low-latency — decrease batch_max_ms (10–25ms) for near-real-time durability at the cost of more frequent transactions.
  • Recovery time budget — tune snapshot_every_events so the worst-case replay count (events since last snapshot) fits your recovery SLA. At 10,000 events/second, snapshot_every_events = 10000 means ≤1 second of replay.
  • Storage — monthly partitions let you drop old data with DROP TABLE events_y202506 rather than DELETE (which vacuums). No application-level partition dropping is built in — manage retention externally or with cron.

Disabling persistence

Omit the [database] section entirely:

# No [database] = noop persistence (in-memory only)
[server]
# ...

All events will be published to subscribers and the TUI will function, but no data survives a restart.
