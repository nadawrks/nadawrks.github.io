NadaTrade Documentation

Deployment

This guide covers deploying NadaTrade on a server for multiple remote users — on your LAN, VPS, or cloud instance. All participants connect to this single host.

Choose Your Method

MethodBest forComplexity
Docker ComposeVPS, cloud instances, quick setupLow
Bare-metal + systemdDedicated servers, low-latencyMedium
Binary downloadDevelopment, CI pipelinesLow

Docker Compose (Recommended)

The repo includes docker-compose.yml for a production-ready stack with PostgreSQL 16 and the nadatrade binary.

git clone https://github.com/nadawrks/nadatrade
cd nadatrade
cp .env.example .env

Configure Secrets

Edit .env with strong values. At minimum:

NADATRADE_JWT_SECRET=$(openssl rand -hex 32)
PG_PASSWORD=$(openssl rand -hex 16)

The .env file is in .gitignore — never commit it.

Start the Stack

docker compose up -d

This starts two services:

  • postgres — PostgreSQL 16, data persisted in the pgdata named volume
  • nadatrade — the exchange binary, maps ports 9823 (FIX) and 9824 (WS/HTTP)

Verify

curl http://<server-ip>:9824/healthz
# {"status":"ok"}

Volume Management

Database data survives container restarts via the pgdata volume. To reset everything:

docker compose down -v   # removes volume — data is gone
docker compose up -d     # fresh start

Pull Pre-Built Image

Instead of building locally:

docker pull ghcr.io/nadawrks/nadatrade:latest

Then set NADATRADE_IMAGE=ghcr.io/nadawrks/nadatrade:latest in .env before docker compose up.

Bare-Metal with systemd

For dedicated servers where you want the binary running directly on the host (for lowest latency or custom kernel tuning).

Install

sudo ./deploy/install.sh

This script:

  1. Creates a nadatrade system user
  2. Downloads the latest binary to /usr/local/bin/nadatrade
  3. Generates a random JWT secret
  4. Installs a systemd service at /etc/systemd/system/nadatrade.service

Manage the Service

sudo systemctl start nadatrade
sudo systemctl status nadatrade
sudo systemctl enable nadatrade   # start on boot

View logs:

journalctl -u nadatrade -f

Configuration

The systemd unit reads environment from /etc/nadatrade/env. Add your secrets there:

# /etc/nadatrade/env
DATABASE_URL=postgres://nadatrade:secret@localhost:5432/nadatrade
NADATRADE_JWT_SECRET=<hex-secret>
SIM_MODE=real_time

Binary Download

Download a pre-built binary from the GitHub Releases page:

curl -fsSL https://github.com/nadawrks/nadatrade/releases/latest/download/nadatrade \
  -o /usr/local/bin/nadatrade
chmod +x /usr/local/bin/nadatrade

export DATABASE_URL="postgres://nadatrade@localhost/nadatrade"
export JWT_SECRET="$(openssl rand -hex 32)"
export SIM_MODE="real_time"

nadatrade --config config/nadatrade.toml

Network Configuration

Ports

PortProtocolPurpose
9823TCPFIX 4.2 gateway
9824TCPWebSocket + HTTP (/healthz, /metrics, /v1/admin)

Both ports bind to 0.0.0.0 by default. For a multi-tenant server, you want these reachable by your bot developers. Restrict in config if needed:

[server]
fix_listen_addr = "10.0.0.5:9823"    # internal NIC only
ws_listen_addr = "10.0.0.5:9824"

Firewall

Allow only the ports you need. Example with ufw:

ufw allow 9823/tcp   # FIX
ufw allow 9824/tcp   # WS + HTTP

Do not expose PostgreSQL (5432) to the internet.

TLS Termination

NadaTrade FIX and WebSocket protocols do not include native TLS. Use a reverse proxy or tunnel for encrypted transport.

Option 1: Reverse Proxy (Recommended)

Use nginx or Caddy to terminate TLS for the WebSocket/HTTP port (9824).

nginx example (/etc/nginx/sites-available/nadatrade):

server {
    listen 443 ssl;
    server_name exchange.example.com;

    ssl_certificate     /etc/ssl/certs/exchange.pem;
    ssl_certificate_key /etc/ssl/private/exchange.key;

    location / {
        proxy_pass http://127.0.0.1:9824;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

Clients then connect to wss://exchange.example.com/v1/orders?token=....

Option 2: stunnel for FIX

FIX clients connect via raw TCP. To encrypt FIX traffic, wrap it with stunnel on both ends:

Server stunnel config (/etc/stunnel/nadatrade-fix.conf):

[fix-tls]
accept  = 0.0.0.0:19823
connect = 127.0.0.1:9823
cert    = /etc/ssl/certs/exchange.pem
key     = /etc/ssl/private/exchange.key

Clients connect to port 19823 (TLS) and stunnel decrypts to 9823 (plain). The FIX client sees a plain TCP stream.

Option 3: VPN / WireGuard

For internal/team use, run nadatrade on a private network (VPC, VPN, WireGuard) and have bot developers connect via VPN. No TLS needed at the application layer.

Multi-Tenant Setup

Participant Registration

Each bot developer needs a participant entry. Add them to participants/participants.toml:

[participants.alice]
comp_id = "ALICE"
display_name = "Alice's Trading Bot"
active = true
initial_cash = { BRL = "1000000.00" }

[participants.bob]
comp_id = "BOB"
display_name = "Bob's Market Maker"
active = true
initial_cash = { BRL = "500000.00" }

Or use the Admin API to add participants at runtime:

curl -X POST http://<host>:9824/v1/admin/participants \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"comp_id":"ALICE","display_name":"Alice","active":true,"initial_cash":{"BRL":"1000000.00"}}'

Distribute Credentials

For each participant, generate a JWT token using your ws_jwt_secret:

import jwt, time
token = jwt.encode(
    {"sub": "ALICE", "exp": int(time.time()) + 31536000},  # 1 year
    secret, algorithm="HS256"
)

Give each developer:

  • Server hostname/IP and port
  • Their JWT token (or the secret to generate their own)
  • FIX credentials if using FIX (username + password from participant config)

Isolation

  • Order fills are private — Alice cannot see Bob’s fills or order book activity
  • Trade prints are public — everyone sees market-wide trades
  • Admin API requires a separate admin JWT token with "role": "admin"
  • Participants operate within their own cash and position limits

Backup & Restore

Database Backup

pg_dump -U nadatrade -h localhost nadatrade > backup.sql

The events table grows continuously. For large deployments, use monthly partition-based backup to skip old partitions:

pg_dump -U nadatrade -h localhost nadatrade \
  --table=events_y202606 --table=events_y202607 \
  --table=snapshots --table=persist_meta \
  > partial_backup.sql

Restore

psql -U nadatrade -h localhost nadatrade < backup.sql

NadaTrade replays events from the last snapshot on restart — no additional restore step needed.

Resource Sizing

WorkloadRAMCPUDisk (events table)
1-5 instruments, 10 bots512 MB1 core~100 MB/day
10-50 instruments, 50 bots2 GB2 cores~1 GB/day
100+ instruments, 100+ bots8 GB4 cores~10 GB/day

These are rough estimates. Actual usage depends on order rate and persistence batch settings.

Connection Limits

The FIX acceptor spawns one tokio task per connection. There is no built-in connection limit — use OS-level limits (ulimit -n) or a connection-counting gauge in the metrics.

Production Checklist

  • Change ws_jwt_secret from changeme
  • Set strong PG_PASSWORD
  • Enable TLS (reverse proxy or stunnel)
  • Restrict fix_listen_addr / ws_listen_addr if not all interfaces needed
  • Configure firewall to only expose ports 9823 and 9824
  • Set up Prometheus scraping of /metrics
  • Set up log aggregation (journald or docker logs)
  • Tune persist.snapshot_every_events for your recovery SLA
  • Configure database backups (at minimum, pg_dump cron)
  • Test recovery from backup before going live
