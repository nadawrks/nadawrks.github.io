NadaTrade Documentation

FIX Messages

NadaTrade implements the FIX 4.2 protocol over TCP. This reference documents every supported message type, tag table, and wire example. All examples use pipe (|) as the field delimiter for readability; on the wire the delimiter is the ASCII SOH character (\x01).

1. Connection Setup

Transport

Clients connect to NadaTrade via raw TCP. The acceptor binds to a configurable SocketAddr and spawns one tokio task per connection.

BodyLength Framing (tag 9)

FIX messages are delimited by the BodyLength field (tag 9). The value of tag 9 is the number of bytes between the delimiter after tag 9 and the delimiter immediately before tag 10 (the checksum). In other words, it counts the length of the message body starting at the first byte of tag 35.

8=FIX.4.2|9=NNN|35=D|...body...|10=CCC|
                 ^^^^^^^^^^^^^^^^
                 This is the BodyLength range

Each complete message is extracted from the TCP stream by:

  1. Locating the 8=FIX.4.2| begin string.
  2. Reading the 9= value to determine the body length.
  3. Reading body_length bytes for the body.
  4. Reading the 10=CCC| checksum trailer.

CheckSum (tag 10)

The checksum is the sum of all byte values from (and including) the 8 of 8=FIX.4.2 through the | that immediately precedes tag 10, modulo 256. The result is zero-padded to three digits.

checksum = sum(bytes of "8=FIX.4.2|9=NNN|...body...") % 256

SOH Delimiter

On the wire, fields are separated by ASCII \x01 (Start of Header). In documentation and examples in this reference, | is used instead.

2. Admin Messages

All admin messages include the standard header tags 8, 9, 35, 49, 56, 34 and the trailer tag 10.

ResendRequest (35=2)

Requests retransmission of messages from a range of sequence numbers. NadaTrade replays messages from its persistent MessageStore.

Resets the sequence number. Used to recover from gaps.

Sequence Number Management

NadaTrade maintains independent inbound and outbound sequence numbers per session.

  • Inbound: tracked as last_seq_num_in on the session. When a message arrives with 34 > last_seq_num_in, a ResendRequest (35=2) is sent for the missing range (last_seq_num_in, 0).
  • Outbound: tracked with an AtomicU64 counter. Each outbound message increments it with fetch_add(1, SeqCst).
  • Initiating seq numbers from the client’s Logon: if the Logon contains 141=Y (ResetSeqNumFlag), both sides reset to 1.

Subscription Tracking

The acceptor maintains a HashMap<String, MdSubscription> per connection. Subscriptions are identified by instrument. On SubscriptionRequestType=2 (unsubscribe), the entry is removed. Market data events (BookUpdated, TradePrinted) are dispatched only to connections subscribing to the relevant instrument.

Role Enforcement

NadaTrade enforces session roles at the protocol level:

  • MarketData-only sessions: Reject 35=D, 35=F, 35=G with SessionReject (35=3).
  • OrderEntry-only sessions: Reject 35=V with SessionReject (35=3).
  • Both (default): All message types accepted.

8. NadaTrade Custom Tags

NadaTrade uses several tags outside the standard FIX 4.2 tag space for features not covered by the base specification.

Tag 7928 — StpMode (Self-Trade Prevention)

Custom tag used on 35=D (NewOrderSingle) and 35=G (CancelReplaceRequest). Controls how self-trade prevention is applied.

ValueSTP ModeDescription
0CancelAggressiveCancel the aggressive (incoming) order if it matches a resting order from the same participant. Default.
1CancelRestingCancel the resting order; let the aggressive order through
2CancelBothCancel both the resting and aggressive orders
3NoneDisable self-trade prevention for this order

Tag 210 — MaxFloor (Display Qty / Iceberg)

Standard FIX tag repurposed by NadaTrade to specify the visible (display) quantity for iceberg orders. When set, the order’s total quantity (tag 38) is hidden; only the display quantity (tag 210) is visible in the order book. The remaining quantity is replenished from the hidden reserve as the visible portion is filled.

Tags 553/554 — Username / Password

Custom tags for FIX session authentication. These are validated against the participant credentials configured in the system. If credentials is non-empty on the session, logon is rejected for:

  • Unknown usernames (no match in credentials map)
  • Incorrect passwords
  • Empty usernames

9. Session State Machine

A FIX session goes through the following states:

  1. Disconnected: No TCP connection. The acceptor waits for connections.
  2. Connected, not logged on: TCP established. All non-Logon messages are rejected with a SessionReject (35=3) containing 58=Session not logged on; send Logon first.
  3. Logged on: A valid Logon has been received. All message types flow according to the session role.
  4. Logout received / connection dropped: Session returns to disconnected state.

During the logged-on state:

  • Heartbeats are sent at the configured interval (heartbeat_interval_secs, default 30s).
  • Sequence number gaps in inbound messages trigger automatic ResendRequests.
  • MessageStore persistence is initialized after a successful logon, storing outbound messages in append-only .fixlog files.

10. MessageStore Persistence

Each FIX session stores outbound messages in a file named {sender}-{target}.fixlog in the configured store directory. The file format is:

{"last_seq_in":<u64>,"last_seq_out":<u64>}
{"seq":<u64>,"msg":"<escaped fix message>"}
{"seq":<u64>,"msg":"<escaped fix message>"}
...
  • Line 1: JSON header with last known sequence numbers (used for recovery).
  • Subsequent lines: One JSON entry per outbound message, with the sequence number and the full FIX message string.
  • The in-memory buffer holds up to cap (default 1000) messages in a VecDeque.
  • ResendRequest (35=2) replays from this buffer, filtering by the (BeginSeqNo, EndSeqNo) range.
